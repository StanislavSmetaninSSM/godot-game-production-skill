# Distinctive mechanic cards and interactions

Use when defining or materially redesigning a core/signature mechanic, or when a
playtest calls its rule into question. Reuse approved decisions first. Routine
implementation, parameter tuning and unrelated maintenance do not require a new
idea round. This reference works inside existing brainstorming/Spec Kit approval.

## Produce a small, meaningful choice

Take the player's main verb and the approved experience. Useful prompts are a risky
alternative to a safe action, a constraint with a payoff, a second use of an existing
verb, or a productive interaction between existing systems. Filter against the
project's pillars, exclusions, budget and prior rejections. Size the alternatives to
the unresolved decision; do not enforce a universal card count or invent new work
at every phase. Renaming a rejected rule does not answer its recorded failure.

Write each candidate as a short card in the existing feature spec or linked design
notes, not a parallel design database:

| Required slot | Concrete content |
|---|---|
| Rule | What the player can do and which consequence changes. |
| Player value | Intended experience and an observable behavior prediction. |
| Fit | Pillar served, exclusions preserved and relevant prior rejection. |
| Experiment | Smallest gym/route, comparison and observation that can disconfirm it. |
| Cost and risk | What production work/assets/state changes it needs and why it may fail. |
| Interaction | Relevant shared owner/resource, competing transitions and a causal test. |
| Disposition | Proposed/selected/rejected/deferred, reason and actual approval/scope linkage. |

For example, two relic/gate alternatives can compare **committing by leaving the
relic at the trigger** with **trading carrying progress for repositioning by dropping**.
The first risks an unrecoverable item; the second risks becoming passive waiting.
Describe the commit/retrieve/expiry experiment and reachable reset in each proposed
card. After selection, exercise only the selected rule against the current baseline.
Costs depend on the existing owner transitions and room, not merely the idea's name.

## Check synergies where rules meet

Use a small mechanic × mechanic matrix for consequential intersections, not every
Cartesian pair. A useful cell records:

`starting state → inputs/order → authoritative owner transitions → priority/conflict
resolution → visible consequence → failure/recovery test`

In the relic example, CarryState publishes the real held/dropped transition and the
gate owner decides eligibility. Specify pickup versus expiry priority and verify
exactly one timer transition plus a reachable retry. Consumers do not shadow either
fact. Tie the case to the existing playtest matrix in `gameplay-evidence.md` and the
single-owner rules in SKILL.md. A successful isolated gym does not prove the combined
route, progression balance or session quality.

## Adopt through the existing authority

The implementation handoff names the selected card, approved baseline/comparator,
authorized experiment scope and source of authority. Unselected cards remain proposals.
Comparing unchosen rules means design comparison until a specifically authorized
comparative probe permits their implementation. Observing existing working behavior
or running an already authorized probe does not grant a new rule's implementation.

Show the unresolved material alternatives and their tradeoffs for the user's choice,
or follow an explicit existing delegation within its exact scope. Record actual
selection rather than labelling an agent's preference as user approval. A prior
specific approval also approves faithful Spec Kit recording; do not ask again just
because a card or document was written. After selection, update the same plan/tasks,
check consistency and test with `mechanic-playtests.md` before multiplying content.
New visual direction still re-enters the existing visual approval/generation chain.
